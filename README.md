# Vector Voice Agent — «мозг» голосового бота автошколы

Агентский сервис на **LangGraph Server**: принимает историю звонка от голосового
бота, решает, о чём говорить дальше, и отдаёт реплику потоком. Голоса, звука и
телефонии здесь нет — этим занимается бот.

```
LiveKit ─── voice_bot (VAD, STT, TTS)
                │  172.17.0.1:8127
                │  ├─ vector_agent    основной ход, когда клиент договорил
                │  └─ vector_checker  лайв-канал, пока клиент говорит
                ▼
         vector_voice_agent  (LangGraph Server + postgres + redis)
                │  host.docker.internal:8317
                ▼
            vector_kb  (справочник: 41 город, 235 филиалов)
```

Общей docker-сети между стеками нет: каждый публикует порт на хост.

---

## Зачем он нужен

Бот на голом системном промпте выдумывает цену, адрес и даты и сворачивает
разговор раньше времени. Сервис лечит и то, и другое:

* **В справочник ходит код, а не модель.** Что принести — записано в шаге
  скрипта. Не «модель решила позвать инструмент», а «дошли до шага о цене —
  значит идём за ценой». Инструмент у модели стоил бы двух обращений к ней за
  ход плюс сам поход: лишняя секунда молчания в трубке.
* **Куда идти дальше по скрипту, решает код.** Модель разбирает ответ клиента и
  формулирует реплику; выбор шага, счётчики и статусы — расчёт.

## Два канала

Каналов два, они работают одновременно и независимо.

| | Когда | Что делает |
|---|---|---|
| **лайв-канал** `vector_checker` | пока клиент говорит | закрывает шаги, греет контекст |
| **канал генератора** `vector_agent` | когда клиент договорил | берёт открытые шаги и говорит |

Общее у них одно — **скрипт разговора в кеше**: один закрывает, другой берёт.
Кеш ключуется идентификатором звонка, а не тредом, поэтому каналы могут жить на
разных тредах LangGraph и не мешать друг другу. Тред сериализует запуски: пока
тред был общий, служебный проход вытеснял основной ход и звонок рвался.

Запись в кеш точечная. Генератор пишет счётчик попыток и пометку взятия, чекер —
статусы и профиль. При одновременной записи ничего не затирается.

**Живой ход всегда главнее фоновой подготовки.** Лайв-канал не имеет права
отменить, задержать или перебить идущий ход. Не успел — ход идёт без него.

## Как устроен ход

```
__start__
    │
 ingest            принять историю, поднять скрипт из кеша
    ├──► lookup    достать из справочника то, что нужно ближайшему шагу
    │       │
    └───────┴──► plan      КОД выбирает шаги в шапку и плюсует им счётчик
                   │
                respond    единственный вызов модели: формулирует реплику
                   │
                commit     фиксирует произнесённое, счётчик, профиль
                   │
                __end__
```

`ingest` расходится на `lookup` и дальше сходится в `plan`: резолвер справочника
не ждёт ничего и работает параллельно приёму хода.

Граф вызывается заново на каждую реплику клиента: отработал, отдал текст, умер.
Паузу «клиент думает» держит телефонная линия, очередью хода управляет бот.
`interrupt()` не используется.

**Чекера в основном ходе нет.** Он живёт только в лайв-канале, на своём треде.
Раньше одна и та же реплика разбиралась дважды, и второй разбор стоил секунды на
горячем пути.

**Один вызов модели на ход.** Разобранный ответ клиента, статус шага и текст
реплики приезжают вместе, одной схемой. Ответ на шаг и посторонний вопрос — два
независимых поля: «Механика. А сколько стоит?» это и то, и другое сразу.

**Реплика звучит по мере генерации.** Схема передаётся в модель словарём, а не
Pydantic-классом: с классом LangChain ставит парсер, который срабатывает один раз
на готовом ответе, и в трубке это секунды тишины. Со словарём работает
`JsonOutputParser`, и прирост текста уходит в эфир кусками. Куски склеиваются
встык — пробелы уже содержатся в токенах, добавлять ничего нельзя.

**Счётчик считается по взятию.** Плюс единица достаётся всем шагам шапки, а не
одному ведущему: генератор говорит по любому из них, и для чекера шаг считается
заданным с того момента, как попал в шапку. Иначе шаг звучит на ход раньше, чем
становится видимым, и закрытия отстают.

## Скрипт разговора

Скрипт — это **данные**, а не код. В репозитории живут четыре версии; актуальный
формат — **v4, скрипт продаж**.

```
источник (JSON → потом личный кабинет)  →  build_script (вся валидация)
                                                  │
                                          CompiledScript  ← неизменяемый, в кэше
                                                  │
                                  в состоянии только id + версия + статусы
```

Версия обязательна. Каждый ход — новый запуск на сервере, поэтому в состоянии
лежит точная версия, и скомпилированный объект берётся из кэша по ней. Выкатили
новый скрипт посреди смены — идущие звонки доигрывают на своей.

### Шаг формата продаж

Шесть полей, пять из них заполняет заказчик:

| Поле | Что в нём |
|---|---|
| `id` | слаг, служебный |
| `name` | название по-русски: «Выявление города», «Возражение: дорого» |
| `order` | число, задаёт порядок |
| `requirements` | что сделать и зачем; для возражений — условие включения первой строкой; что записать в форму — с именем поля; чего на этом шаге нельзя |
| `examples` | две-три живые формулировки, **не для зачитывания** |
| `knowledge` | список фактов из базы, которые шагу нужны; пустой — не нужны |

Название шага уходит в промпт вместе с требованиями: модель видит, на каком этапе
продажи идёт разговор.

**Технических полей в файле нет.** Счётчик попыток ставит генератор при взятии
шага, признак закрытия ставит чекер, форму заполняет заполнитель полей — всё это
живёт в кеше по ключу звонка.

**Правил речи и персоны в скрипте тоже нет.** Граница простая: в скрипте — что
говорим, в коде — как говорим. «Вы», имя без отчества, запрет канцелярита
одинаковы для автошколы, банка и стоматологии, и заказчик их переписывать не
должен. Персона агента — настройка (`AGENT_NAME`, `AGENT_ROLE`, `AGENT_GENDER`).

**Скрипт не несёт фактов.** Срок обучения, цены, расписания, скидки, тарифы,
взносы приходят из базы через контекстер. Исключение — установленное законом и
одинаковое везде: налоговый вычет, состав медкомиссии, возраст допуска. Нет
факта в контексте — он не звучит, но шаг не пропускается: ход к человеку делается
без чисел.

### Старые версии

v1, v2 и v3 собираются как раньше и лежат рядом. У них другой формат шага —
`kind`, `fills`, `requires`, `after`, `needs`, `verbatim`, `branches`. Лишние
ключи `persona` и `rules` в них игнорируются молча.

### Цена

Три ветки, и ветка выбирается **по полям ответа справочника**, а не по списку
городов и не по константам:

| Ответ API | Что говорим |
|---|---|
| суммы нет | цену не называем, зовём на оформление |
| сумма есть, `reliable: false` | называем как примерную «от» |
| сумма есть, `reliable: true` | называем как точную |

Поле `note` из справочника вслух не произносится: оно написано под передачу
менеджеру, а бот и есть менеджер. Истина — `amount` и `reliable`, формулировка
наша.

### Город

Опора — перечисление `/cities/enum`: модель выбирает слаг из готового списка,
поэтому промахнуться мимо существующего города нельзя по построению.
`/cities/resolve` остаётся быстрым путём на точное совпадение. Город зафиксирован
в состоянии — мету тянем один раз и держим весь разговор.

Районы в справочнике заполнены у трёх филиалов из 235, поэтому филиал подбирается
перечислением адресов и ориентиров вслух.

## Диагностика

Ход читается по логу одной командой:

```bash
docker compose logs vector-agent-api --no-log-prefix \
  | grep -E "\[(plan|live-check|check)\|"
```

| Строка | Что показывает |
|---|---|
| `[plan\|done]` | ведущий шаг, шапка со счётчиками, звонок, город, филиал |
| `[live-check\|state]` | счётчики, статусы и заполненные поля, которые увидел чекер |
| `[check\|pending]` | что ушло на проверку и почему остальное отсеяно |
| `[llm\|done]` | время каждого вызова модели: чекер, резолвер, генератор |

Здоровый ход: шаг попадает в `[check|pending]` тем же ходом, на котором
прозвучал; `[plan|done]` идёт по возрастанию `order`; ход укладывается в
1,2–1,8 секунды.

### Переменные

Обязательная одна — ключ OpenAI. Остальные со значениями по умолчанию:

| Переменная | По умолчанию | Зачем |
|---|---|---|
| `SCRIPT_ID` | `vector_ru` | какой скрипт грузим |
| `SCRIPT_VERSION` | не задана | **задать явно**: иначе берётся последняя из каталога |
| `LLM_MODEL` | `gpt-4.1-mini` | модель служебных вызовов |
| `LLM_TEMPERATURE` | `0.6` | температура генератора |
| `TURN_BUDGET_SECONDS` | `9.0` | потолок ожидания на ход |
| `STEP_ATTEMPT_LIMIT` | `2` | сколько раз шаг может уйти в шапку |
| `PENDING_STEPS_SOFT_CAP` | `4` | потолок висящих шагов в шапке |
| `CHECKER_MIN_GROWTH_CHARS` | `10` | порог прироста для лайв-прохода |
| `VECTOR_KB_CACHE_TTL` | `3600` | кеш справочника, секунды |
| `LIVE_THREAD_SUFFIX` | `-live` | запасной путь опознания лайв-треда |
| `AGENT_NAME` / `AGENT_ROLE` / `AGENT_GENDER` | Дарья / менеджер / female | персона |

## Подключение бота

Бот зовёт два графа: `vector_agent` на своём треде и `vector_checker` на
отдельном, передавая в `configurable` поле `call_id` — идентификатор звонка,
равный треду основного хода. По нему оба канала находят один скрипт в кеше.

Выкатывать мозг и бота нужно **вместе**: бот с новым лайв-тредом против старого
мозга положит скрипт на два разных ключа, и каналы разъедутся.
