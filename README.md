# vector_voice_agent — мозг

Агентский сервис на **LangGraph Server**. Получает от бота историю звонка,
решает, о чём говорить дальше, и отдаёт реплику потоком. Звука, голоса и
телефонии здесь нет.

Здесь же живёт скрипт продаж и вся дисциплина разговора: какие шаги пройти, что
считать закрытым, что можно произносить вслух, а что — нет.

Главное решение сервиса объясняется одной фразой: **бот на голом системном
промпте выдумывает цену, адрес и даты**. Поэтому в справочник ходит код, а не
модель, и выбор следующего шага — тоже расчёт, а не решение модели. Модель
разбирает ответ клиента и формулирует реплику; всё остальное считается.

---

## Место в связке

```
voice_bot ──┬──▶ vector_agent    основной ход, когда клиент договорил
            └──▶ vector_checker  лайв-канал, пока клиент говорит
                      │
                      ├──▶ vector_kb   справочник: города, филиалы, цены
                      ├──▶ Redis       прогресс скрипта и контекст звонка
                      └──▶ Postgres    служебное состояние LangGraph
```

**Кто его зовёт.** Только голосовой бот, двумя независимыми каналами. Каналы
работают одновременно и на разных тредах.

| Канал | Когда | Что делает |
|---|---|---|
| `vector_agent` | клиент договорил | берёт открытые шаги и говорит |
| `vector_checker` | пока клиент говорит | закрывает шаги, греет контекст, решает конец разговора |

**Кого зовёт он.**

| Куда | Зачем | Если не отвечает |
|---|---|---|
| `vector_kb` | цены, филиалы, города | факта нет — он просто не звучит, шаг при этом не пропускается |
| Redis | прогресс скрипта и контекст разговора | каналы перестают видеть работу друг друга |
| Postgres | чекпоинты LangGraph Server | сервер не поднимется |
| провайдер LLM | формулировка реплики | по исчерпании бюджета хода — аварийная реплика из настроек, а не молчание |

**Что будет, если не отвечает мозг.** Ход не состоится, в трубке пауза. Бот
разово пробует `GET /ok` при старте и пишет результат в лог, но звонки этим не
блокирует.

---

## Два канала, один скрипт

Общее у каналов — **скрипт и контекст разговора в Redis**: один закрывает шаги,
другой их берёт. Кеш ключуется идентификатором звонка (`call_id` из
`configurable`), а не тредом — поэтому каналы живут на разных тредах LangGraph и
не мешают друг другу.

Так сделано не из красоты. Тред сериализует запуски: пока тред был общий,
служебный проход выталкивал основной ход и звонок рвался.

Запись в кеш точечная: генератор пишет счётчик попыток и пометку взятия, чекер —
статусы и профиль. При одновременной записи ничего не затирается.

**Живой ход всегда главнее фоновой подготовки.** Лайв-канал не имеет права
отменить, задержать или перебить идущий ход. Не успел — ход идёт без него.

---

## Как устроен ход

```
__start__ → ingest → plan → respond → commit → __end__
```

- `ingest` — принять историю, поднять скрипт, сверить произнесённое;
- `plan` — **код** выбирает шаги в шапку и плюсует им счётчик;
- `respond` — единственный вызов модели: формулирует реплику;
- `commit` — фиксирует произнесённое, счётчик, профиль.

Чекера в основном ходе нет: он живёт только в лайв-канале. Раньше одна и та же
реплика разбиралась дважды, и второй разбор стоил секунды на горячем пути.

Граф вызывается заново на каждую реплику: отработал, отдал текст, умер. Паузу
«клиент думает» держит телефонная линия, очередью хода управляет бот.
`interrupt()` не используется, чекпоинтер серверный.

**Реплика звучит по мере генерации.** Схема передаётся в модель словарём, а не
Pydantic-классом: с классом LangChain ставит парсер, который срабатывает один
раз на готовом ответе, и в трубке это секунды тишины.

**Счётчик считается по взятию шага в шапку**, а не по ведущему шагу. Генератор
может заговорить по любому шагу из шапки, и для чекера шаг считается заданным с
момента попадания туда.

## Скрипт разговора

Скрипт — это **данные**, а не код. В `src/script/data/` лежат четыре версии
(`vector_ru.v1` … `v4`); актуальный формат — **v4, скрипт продаж**.

Версия закрепляется явно и хранится в состоянии звонка. Выкатили новый скрипт
посреди смены — идущие звонки доигрывают на своей версии.

Шаг формата продаж — шесть полей, пять из них заполняет заказчик: слаг,
название по-русски, порядок, требования (что сделать и зачем; для возражений —
условие включения первой строкой), две-три живые формулировки как образцы (не
для зачитывания) и список фактов из базы, которые шагу нужны.

Три правила про содержимое скрипта:

1. **Технических полей в файле нет.** Счётчики, признаки закрытия и форма живут
   в кеше по ключу звонка.
2. **Правил речи и персоны в скрипте нет.** Граница: в скрипте — *что* говорим,
   в коде — *как* говорим. Персона задаётся настройками.
3. **Скрипт не несёт фактов.** Сроки, цены, расписания, скидки приходят из
   справочника. Исключение — установленное законом и одинаковое везде:
   налоговый вычет, состав медкомиссии, возраст допуска.

### Цена

Ветка выбирается **по полям ответа справочника**, а не по списку городов:

| Ответ справочника | Что говорим |
|---|---|
| суммы нет | цену не называем, зовём на оформление |
| сумма есть, не подтверждена | называем как примерную «от» |
| сумма есть, подтверждена | называем как точную |

Поле `note` из справочника вслух не произносится: оно написано под передачу
менеджеру, а бот и есть менеджер.

Старые версии скрипта (v1–v3) собираются как раньше и лежат рядом; у них другой
формат шага, а лишние ключи игнорируются молча.

## Локальный запуск

Нужен `uv`. Образ сервера собирается **не** `docker build`, а CLI LangGraph —
своего `Dockerfile` в репозитории нет и не должно быть.

```bash
uv sync --all-extras          # обязательно --all-extras: dev-зависимости в extras

make dev                      # граф в памяти, для Studio: без postgres и redis
make build_image              # langgraph build
make up                       # postgres + redis + сервер
make ok                       # проверка живости
```

`make dev` — самый быстрый способ покрутить логику: поднимает граф локально, без
хранилищ.

**Как убедиться, что работает.** `GET /ok` отвечает 200. Дальше смотреть лог
одного хода:

```bash
docker compose logs vector-agent-api --no-log-prefix | grep -E "\[(plan|live-check|check|llm)\|"
```

| Строка | Что показывает |
|---|---|
| `[plan\|done]` | ведущий шаг, шапка со счётчиками, звонок, город, филиал |
| `[live-check\|state]` | счётчики, статусы и заполненные поля глазами чекера |
| `[check\|pending]` | что ушло на проверку и почему остальное отсеяно |
| `[llm\|done]` | время каждого вызова модели |

Здоровый ход: шаг попадает в `[check|pending]` тем же ходом, на котором
прозвучал; `[plan|done]` идёт по возрастанию порядка шагов.

## Переменные окружения

Только имена и назначение.

**Модель.** `LLM_BASE_URL`, `LLM_API_KEY` — любой OpenAI-совместимый провайдер;
меняется без правок кода. `LLM_MODEL` — основная модель хода, `LLM_MODEL_FAST` —
быстрая для коротких служебных вызовов (пусто — берётся основная).
`LLM_TEMPERATURE`, `LLM_MAX_CONCURRENCY`, `LLM_MAX_TOKENS`,
`LLM_MAX_TOKENS_SHORT`.

**Бюджет хода.** `LLM_CONNECT_TIMEOUT`, `LLM_READ_TIMEOUT`,
`TURN_BUDGET_SECONDS`. Промах бюджета — аварийная реплика, а не бесконечное
ожидание: в звонке пауза дороже плохого ответа. `LADDER_DEADLINE_SECONDS` —
потолок лестницы заглушек, пока фон добывает данные.

**Скрипт.** `SCRIPT_ID`, `SCRIPT_VERSION` (**задавать явно**, см. грабли),
`SCRIPT_DIR`, `SCRIPT_REDIS_TTL`, `STEP_ATTEMPT_LIMIT`, `PENDING_STEPS_SOFT_CAP`,
`WAITING_HISTORY_LIMIT`.

**Справочник.** `VECTOR_KB_URL`, `VECTOR_KB_TIMEOUT`, `VECTOR_KB_CACHE_TTL`.
Подбор ближайшего филиала: `NEAREST_BRANCHES_ENABLED`, `NEAREST_BRANCHES_LIMIT`,
`NEAREST_BRANCHES_RADIUS_KM`, `GEOCODE_TIMEOUT_SECONDS`.

**Лайв-канал.** `CHECKER_MIN_GROWTH_CHARS` — порог прироста текста между
служебными проходами. `CHECKER_GRAPH_ID`, `CHECKER_MULTITASK_STRATEGY`,
`AGENT_MULTITASK_STRATEGY`, `FAREWELL_MIN_MESSAGES`, `LIVE_THREAD_SUFFIX`.

**Персона.** `AGENT_NAME`, `AGENT_COMPANY`, `AGENT_ROLE`, `AGENT_TONE`,
`AGENT_GENDER` (из него собирается правило о роде в промпте), `AGENT_FALLBACK`,
`AGENT_UNKNOWN`, `AGENT_PRICE_NO_AMOUNT`, `AGENT_PRICE_UNRELIABLE`,
`AGENT_PRICE_RELIABLE`.

**Хранилища и прокси.** `REDIS_URI`, `DATABASE_URI` (последнюю задаёт compose).
`IS_PROXY` — главный выключатель; при выключенном заполненные `PROXY_HOST`,
`PROXY_PORT`, `PROXY_USER`, `PROXY_PASS`, `PROXY_SCHEME` игнорируются целиком.

**Наблюдаемость.** `LOG_LEVEL`, `LANGSMITH_PROJECT`, `LANGSMITH_API_KEY`
(пусто — трейсы выключены).

Необязательные строковые поля приводят пустую строку к «не задано» валидатором:
`SCRIPT_VERSION=` означает «взять последнюю», а не «искать версию с пустым
именем».

## Структура

```
src/
├── core/config.py        все настройки, вся валидация окружения
├── graph/
│   ├── graph.py          основной ход: ingest → plan → respond → commit
│   ├── checker_graph.py  лайв-канал одним узлом
│   ├── nodes.py          узлы основного хода
│   ├── state.py          состояние звонка и контекст запуска
│   ├── prompts.py        сборка промптов (самый большой модуль)
│   ├── checker.py        что считать закрытым
│   ├── contexter.py      добыча данных под предстоящий шаг
│   ├── context*.py       единый документ контекста и его хранилище
│   ├── nearby.py         подбор ближайшего филиала
│   ├── profile_*.py      разбор и форма профиля клиента
│   ├── farewell_agent.py решение о конце разговора
│   └── log_fmt.py        формат диагностических строк
├── script/               скрипт как данные: источник, сборка, планировщик, цена
│   └── data/*.json       версии скрипта
├── kb/client.py          клиент справочника с кешем
└── utils/llm_gen.py      обвязка вызова модели
```

Куда смотреть:

- поменять тексты и порядок разговора — JSON в `script/data/`, код не трогать;
- поменять правила речи и персону — `core/config.py` и `graph/prompts.py`;
- поменять, что считать закрытым шагом — `graph/checker.py`;
- поменять, какие факты тянутся под шаг — `graph/contexter.py` и
  `graph/tools_registry.py`;
- подключить скрипты из личного кабинета вместо JSON — `script/source.py`, это
  единственная точка подмены, и она обязана остаться бесшовной.

## Чего здесь нет намеренно

Своего `Dockerfile` — образ делает `langgraph build`. Своей телефонии, TTS и
STT — это бот. Инструментов у модели для похода в справочник: за данными ходит
код по шагу скрипта, потому что инструмент стоил бы двух обращений к модели за
ход плюс сам поход — лишняя секунда молчания в трубке.

## Известные грабли

**Мозг и бот выкатываются вместе.** Они делят состояние звонка по ключу,
который бот считает из имени комнаты. Разъехались версии — ключ разошёлся,
каналы работают с разными скриптами, и разговор поедет с начала посреди звонка.
**В логах не будет ни одной ошибки.** Проверять `make check` в инфраструктуре —
он сверяет даты сборки образов бота и мозга.

**`SCRIPT_VERSION` надо пинить явно.** Пустое значение означает «последняя
версия из каталога». Выложили новый файл — и все идущие звонки переключатся на
него без обкатки. Это же проверяет `make check` в инфраструктуре.

**Бюджет хода — не таймаут провайдера.** `TURN_BUDGET_SECONDS` считается на весь
ход и по исчерпании отдаёт аварийную реплику из настроек. Если поднять его «на
всякий случай», человек будет слушать тишину вместо честного «повторите,
пожалуйста».

**В контейнере нет `curl`.** Образ собран `langgraph build`. Собственный
`docker-compose.yml` репозитория проверяет живость через `curl -fsS` — в
инфраструктурном compose тот же эндпоинт проверяется через `python -c "import
urllib.request..."`, и это правильный вариант.

**Пустая переменная и отсутствующая — разные вещи.** Для обязательных строк
пустое значение проходит проверку типа, но ломает смысл. Здесь это частично
закрыто валидатором, приводящим пустые строки к «не задано», но привычка
обнулять переменные пустой строкой в общем `.env` стека уже роняла соседние
сервисы.

**Общий `.env` раздаёт переменные всем контейнерам.** Всё, что описывает
устройство конкретного образа (пути внутри, порты, имена вроде `HF_HOME`),
должно жить в `environment:` своего сервиса, иначе `env_file` разнесёт это по
всем и перебьёт чужие настройки.

**Логи мозга шумные.** В инфраструктуре `make logs-dump` отфильтровывает
служебный поток (`metrics_collector`, `pool_stats`, `Worker stats`) — без этого
разбирать звонок тяжело. Снимать логи нужно сразу после звонка: окно ротации
короткое.
